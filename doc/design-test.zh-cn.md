# 设计：测试套件

> 本文是 [design-test.md](design-test.md) 的中文译本。

本库**如何**测试：什么在哪里测、套件如何运行，以及所需的环境。这是从 [design.zh-cn.md](./design.zh-cn.md)
拆出的一个主题。

## 原则

- 通过公共 API 进行的测试（单个类对接伪对端、两个类端到端互测、构建产物）检查 `spec-*` 系列规定的
  行为，而不是以当前代码为准。`src/util.js` 中各函数的测试检查 `design.zh-cn.md` 描述的机制。
- 由 `src/util.js` 中纯函数实现的规则，在那里逐条测试。类的测试只检查类确实应用了它：通过类测一两个
  用例，不再把整张表重测一遍。
- 代码尚未满足规格之处，测试仍然陈述规格要求的行为，并标记为 `{ todo }`，这样套件能显示缺少什么，
  而不会失败；修复后移除该标记。
- 不需要额外的测试依赖：套件使用 Node.js 内置的运行器（`node:test`、`node:assert/strict`）。
- 除构建产物测试外，测试直接从 `src/` 导入，因此源码测试无需构建。

## 分层

`test/util.test.js` 覆盖 `src/util.js`；`test/client.test.js` 和 `test/server.test.js` 分别单独
覆盖一个类；`test/tcp.test.js`、`test/serial.test.js` 和 `test/serial-bridge.test.js` 分别通过回环
TCP、一对串口和模拟串行线路对两个类做端到端测试；`test/bundle.test.js` 覆盖构建产物 `dist/modbus.js`
及 `native/`。夹具位于 `test/helpers.js` 和 `test/serial-bridge.js`。

## 命令

| 命令                 | 作用                                                                  |
| -------------------- | --------------------------------------------------------------------- |
| `pnpm test`          | 先运行 `pnpm build`，再用 `node --test` 运行所有 `test/**/*.test.js`。 |
| `pnpm test:coverage` | 同上，并输出仅限 `src/**` 的内置覆盖率报告。                          |

也可以直接运行 `node --test`；此时若 `dist/modbus.js` 不存在，或比 `src/` 中任一文件旧，构建产物测试
会被跳过。

## 伪对端与隔离

- 服务端在 `127.0.0.1` 上以端口 `0` 监听，因此每个测试都会得到一个空闲的临时端口，各测试文件可以
  并行运行。公开选项不接受端口 `0`，因此测试服务端先用固定目标构造，再把它的 `port` 属性设为 `0`
  （`test/helpers.js` 中的 `ephemeral_server`）。
- 客户端测试使用一个原始的 `node:net` 服务端充当伪从站，从而可以检查线路上的确切字节，并构造格式
  错误或乱序的应答。
- 服务端测试在不需要网络时通过伪套接字或伪串口把帧送入 `on_data`；在真实传输有意义时使用原始的
  `node:net` 套接字。
- 串口生命周期测试把 `src/serial.js` 的串口工厂替换为创建伪串口的工厂（`set_serial_port_factory`，
  不属于公共 API），因此不需要串口硬件，也不需要原生绑定。

## 串口测试

串口测试在一条链路上运行，链路的两端由环境变量 `MODBUS_SERIAL_PORTS="<第一端>,<第二端>"` 设置。
串口测试默认关闭，因为一台机器不一定有串口，无论虚拟的还是物理的：未设置该变量时，串口测试组被跳过。

该变量有四种形式。含 `:` 的一端是 TCP 端，其余的是串口设备路径。通常由启动脚本 `pnpm test:serial`
设置它（见下文“串口测试启动脚本”）；也可以手动设置，例如用 `node --test --experimental-test-coverage`
运行串口测试时。

| 形式                                          | 链路                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `COM11,COM12`                                 | 两个像零调制解调器线缆那样相连的串口：一对 com0com 端口，或两个接在一起的物理串口。 |
| `COM3,192.168.1.10:4001`                      | 一个串口接到一台处于 TCP 服务端模式的串口透传设备；测试主动连接它。                 |
| `COM3,192.168.1.10:4001\|192.168.1.10:4002`   | 同上，但使用远程端池：多个以 `\|` 分隔的 `host:port` 端，依次轮换使用。             |
| `COM3,:4001`                                  | 同上，但透传设备处于 TCP 客户端模式；测试在该端口监听，等它连进来。                 |

- **只用透传设备。** TCP 端必须是原样转发字节的透传设备。不支持 Modbus RTU 转 TCP 网关：它会改写
  帧，测试就看不到线路上的字节。测试在 TCP 端使用 RTU-over-TCP。
- **透传设备的连接数。** TCP 服务端模式的透传设备必须接受 2 个以上的 Modbus over TCP 连接。各测试组
  自行打开和关闭 TCP 端，一个紧接一个，不等待透传设备释放连接；只保留一个连接的透传设备在旧连接
  尚未释放时会断开新连接。对这样的透传设备，给出 2 个以上的远程端（例如同一台网关的不同通道）组成
  远程端池。
- **远程端池。** 测试每次连接远程端（预检、原始流测试组、`Modbus_Client` 的 `rtu_over_tcp` 目标）时，
  都取池中的下一个，循环使用，所以相邻两次连接落在不同的远程端上。一次运行没有用到的远程端不算错误：
  被测的是串口。本机监听端 `:port` 始终只有一个，不能放进池中。
- **串口参数。** 测试组以 9600 波特、8 数据位、无校验、1 停止位（9600 8N1）运行，这是 Modbus 常用的
  默认值。透传设备的串口一侧也须设成相同参数。
- **波特率扫描。** 两个串口时，先做一轮扫描：在 1200、2400、4800、9600、19200、38400、57600 和
  115200 波特（8N1）下，各由对端发一个请求并检查应答。某个波特率失败不算错误，因为端口不一定支持
  所有波特率。扫描完成时列出所有成功的波特率，至少一个波特率成功算扫描通过；一个都不成功时扫描失败，
  其余串口测试组不再运行。有 TCP 端时不做扫描，因为透传设备的波特率是固定的。
- **双串口时测试组的波特率。** 9600 是工业默认波特率，只要成功列表中有 9600，其余串口测试组就用它；
  只有成功列表中没有 9600 时，才用列表中的第一个波特率。
- **角色。** 两个串口时，服务端一侧打开第一个端口，对端（原始串口或 `Modbus_Client`）打开第二个。
  有 TCP 端时，被测的库在两种角色下都位于串口一侧，TCP 端是它的对端：按连接方向允许的，用客户端、
  服务端或原始套接字（`Modbus_Server` 只监听，`Modbus_Client` 只主动连接）。
- **设置即必需。** 串口测试组运行前会做一次预检：打开每个串口端，连接（远程端池中的下一个）或等待 TCP 端。设置了
  `MODBUS_SERIAL_PORTS` 而某一端无法使用时，串口测试组失败并注明原因；只有未设置该变量时才跳过。
- **重开串口。** 刚关闭的串口可能在几十毫秒内拒绝重新打开（CH340 驱动上见到过：`Access is denied`）。
  测试每次打开串口时，无论是作为原始流、通过 `Modbus_Server.start()` 还是通过串口 `Modbus_Client`，
  失败都每 20 ms 重试一次，最多 500 ms；超过时限仍失败才报错，所以真正被占用的串口仍会失败。重启测试
  在 `stop()` 与 `start()` 之间停顿 100 ms，因为它检查的是这两个调用，而不是驱动。库本身不重试：打开
  失败交给调用者处理。

### 串口测试启动脚本

`pnpm test:serial`（`test/run-serial.js`）用一条命令在串口的各个方向上运行串口测试。它只负责串口测试，
其余测试用 `pnpm test` 运行。参数有两种形式，第一个参数总是串口（不含 `:`）：

| 形式                                            | 运行（按顺序）                                            |
| ----------------------------------------------- | --------------------------------------------------------- |
| `pnpm test:serial COMn COMm`                    | `COMn,COMm`，然后交换方向 `COMm,COMn`                     |
| `pnpm test:serial COMn [:port] [host:port ...]` | 给了 `:port` 时运行 `COMn,:port`；给了远程端时，然后运行 `COMn,<远程端池>` |

- `:port` 可选，给出时紧跟在串口之后，只有一个。其后可以跟任意多个远程端 `host:port`，组成一次运行的
  远程端池。两者至少给一个；省略其中一个，就只测另一个方向。
- 两种形式不能混合（例如 `COM4 COM5 :502`）：那需要把第一个串口同时接到另一个串口和透传设备上。
- 参数不符合任何一种形式时，打印用法并以退出码 2 结束，不运行任何测试。
- 每次运行是一个 `node --test test/serial.test.js` 子进程，只为它设置 `MODBUS_SERIAL_PORTS`；它退出后才
  开始下一次运行，所以它占用的串口和连接都已释放。两次运行之间不等待：重开串口由上面的打开重试兜底，
  TCP 一侧由透传设备的连接数要求保证。两个串口时，每个方向都运行波特率扫描。
- 某次运行失败不影响其余运行。全部结束后，脚本把每次运行列为 `pass` 或 `FAIL`，任何一次失败则以退出码
  1 结束。
